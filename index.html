Problem-solving

How I approach problems: problem, possible causes, diagnosis, solution, lesson.

Five scenarios based on the work in this portfolio: two from a computer shop like the one where I worked, and three from my own web projects.

Case 1: Computer shop printer not printing (scenario)

Problem: At a computer shop like my aunt's, a customer sent a document to the printer but nothing came out. The file stayed in the print queue, and more customers were waiting for their printouts.

Possible causes: Printer turned off or offline, paper jam or no paper, the wrong default printer selected, or a stuck job in the Print Spooler.

Diagnosis:

  1. Checked the printer itself: it was on, had paper, no jam and no blinking error light.
  2. Printed a test page using the printer's own button. It printed, so the printer was fine and the problem was on the computer side.
  3. Opened the print queue and saw an old job marked "Error" at the top, blocking all the jobs behind it.

Solution:

  1. Cancelled the stuck job. When it would not delete, opened services.msc and restarted the Print Spooler service.
  2. Checked that the correct printer was set as the default printer.
  3. Printed a test page from the computer, then reprinted the customers' documents in order.

Lesson learned: One stuck job can block the whole queue. Test the printer by itself first, so you know if the problem is the printer or the computer.

Case 2: Shop computer has no internet (scenario)

Problem: A customer at the computer shop needed to submit an online form, but one unit showed "No Internet". The other units in the shop were online.

Possible causes: Loose or unplugged LAN cable, network adapter disabled, no IP address from the router, or a wrong DNS setting.

Diagnosis:

  1. The other units worked, so the router and internet line were fine. The problem was only on that unit.
  2. Checked the LAN cable and the port lights at the back of the unit.
  3. Ran ipconfig and saw an address starting with 169.254, which means the unit did not get an IP address from the router.

Solution:

  1. Plugged the LAN cable in firmly until it clicked.
  2. Ran ipconfig /release and ipconfig /renew to get a new IP address.
  3. Opened a website to confirm, then let the customer continue.

Lesson learned: Check if the problem is one device or the whole network first. It tells you where to look and saves time.

Case 3: Images missing on the live GitHub Pages site (scenario)

Problem: Project screenshots like the ones in my Projects section showed on my computer, but after uploading to GitHub Pages some images appeared as broken icons on the live site.

Possible causes: Wrong file path, the image was not uploaded to GitHub, a capital letter in the file name that does not match the code, or a space in the file name.

Diagnosis:

  1. Opened the browser DevTools (F12) and checked the Console. It showed a 404 error for the image file.
  2. Compared the file name in the repository with the name in the code. For example, image/student grade system.png in the code versus Student Grade System.png in GitHub.
  3. Learned that Windows ignores capital letters in file names, but GitHub Pages does not, so it worked on my computer only.

Solution:

  1. Made the path in the code match the real file name exactly, including capital letters.
  2. Replaced spaces with %20 in the path (e.g. image/Student%20Grade%20System.png).
  3. Committed the fix, waited for GitHub Pages to update, and refreshed the live site to confirm all images loaded.

Lesson learned: Always test the live site, not only the local copy. Simple file names without spaces avoid this problem.

Case 4: Student Grade System shows a wrong average (scenario)

Problem: In a grade system like my Student Grade System project, a student with grades 85 and 90 got an average of 4295 instead of 87.5. A wrong grade could be reported to the teacher.

Possible causes: The inputs are read as text, the wrong number of subjects is used in the division, or an empty input is counted.

Diagnosis:

  1. Used console.log() to check the total. It showed "8590" instead of 175.
  2. This means the values from the input boxes were text, so + joined them together instead of adding them.

Solution:

  1. Converted each input to a number with Number(input.value) before adding.
  2. Added a check so empty or invalid grades (below 0 or above 100) show an error message.
  3. Tested known examples by hand: 85 and 90 give 87.5, and 75, 80 and 90 give 81.67.

Lesson learned: Values from forms are always text. Check results with examples I can compute myself, like I do with reports in Excel.

Case 5: To-Do List tasks disappear after refresh (scenario)

Problem: In a task app like my To-Do List App, a user added tasks, refreshed the page, and all tasks were gone.

Possible causes: Tasks were only kept in a JavaScript variable, the save code was not called after adding a task, or the saved data was not loaded when the page opened.

Diagnosis:

  1. Opened DevTools (F12), then Application → Local Storage. There was no saved task list.
  2. Found that tasks were only stored in an array, which resets every time the page reloads.

Solution:

  1. Saved the list after every add, edit or delete with localStorage.setItem("tasks", JSON.stringify(tasks)).
  2. Loaded it when the page opens with JSON.parse(localStorage.getItem("tasks")) || [].
  3. Tested by adding, completing and deleting tasks, then refreshing and closing the browser to confirm they stayed.

Lesson learned: Data in a variable is lost on refresh. If users need it later, it has to be saved somewhere, and I should test what happens after a refresh.

Cybersecurity case study: SQL injection

A defensive look at a common web weakness and how developers prevent it. I built my security basics through three webinars on cyber threats, zero trust and IoT security (see Certificates).

1. What is the vulnerability?

SQL injection happens when an app puts what a user types straight into a database query. The database can't tell the real query from the user's text, so an attacker's SQL can run as part of it.

2. How can it happen?

It happens when a query is built by joining strings. Login forms and search boxes are the usual targets.

✗ Vulnerable: do not use

$sql = "SELECT * FROM users WHERE username = '"
     . $_POST['user'] . "'";

✓ Safe: prepared statement

$stmt = $pdo->prepare(
  "SELECT * FROM users WHERE username = ?");
$stmt->execute([$_POST['user']]);

With a prepared statement, the query is fixed first and the input is sent separately as data.

3. What are the risks?

  • Logging in without a valid password.
  • Reading private data.
  • Changing or deleting records.
  • Legal problems, e.g. under the Data Privacy Act of 2012.

4. How can developers prevent it?

  • Use prepared statements for every query with user input.
  • Validate input type and length.
  • Hash passwords; never store plain text.
  • Give the database account only the permissions it needs.
  • Show generic error messages to users.

5. Security practices

  • Test only on your own system.
  • Keep software updated.
  • Monitor failed logins.
  • Use HTTPS and regular backups.
  • Follow the OWASP Top 10.
